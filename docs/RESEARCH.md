# Research log

External findings that shaped a decision in this repo. Not a link dump — every row changed something (adopted, rejected with a reason, or is still open). Prioritizes official sources and primary documentation over blog posts, per this project's own bias toward verified-over-asserted.

| Date | Source | Finding | Implication | Status | Rationale |
|---|---|---|---|---|---|
| 2026-08-24 | Next.js official docs (`opengraph-image` file convention) | `opengraph-image.tsx` using `ImageResponse` is statically optimized (generated at build time, cached) unless it uses request-time APIs or uncached data | Compatible with `home/`'s `output: "export"` static-export mode, since the page has no dynamic route segments | Adopted | Verified by direct fetch of the official page rather than a search-result paraphrase — the one point of genuine technical uncertainty for the `home/` OG-image work |
| 2026-08-25 | Direct repo audit (this session) | No visual regression / screenshot-diffing tool exists anywhere in the repo (confirmed by search: no `pixelmatch`, no `toMatchSnapshot`, no Percy/Chromatic) despite `tools/screenshots/` already having Playwright + axe-core as dependencies and a capture-only script (`capture.mjs`) | The gap is real and the existing tooling is the right extension point — no need to introduce a parallel Playwright setup | Adopted | Grounded in direct file search, not assumption; shaped the "extend `tools/screenshots/`, don't invent a parallel structure" decision in the visual-regression plan |
| 2026-08-25 | Playwright's `toHaveScreenshot()` vs. `pixelmatch`+`pngjs` (evaluated, not fetched from external docs this pass — general framework knowledge) | `toHaveScreenshot()` requires the `@playwright/test` test runner and its own baseline/threshold/platform-pinning semantics, a bigger dependency and architecture shift than adding a lightweight pure-JS diff library to the existing `playwright-core`-based scripts | `pixelmatch` + `pngjs` chosen for the visual-regression system: no native deps, small footprint, fits the existing `tools/screenshots/` script style (plain `.mjs`, no test-runner wrapper) | Adopted | Open item: this comparison should be re-verified against current Playwright docs before the tool is promoted to a blocking gate, since `toHaveScreenshot()`'s baseline-management ergonomics may be worth the heavier dependency once the system is proven |
| 2026-08-25 | `docs/AUDIT.md` (this repo's own prior self-audit, dated 2026-08-10) | A manual LLM-driven audit found a real stored-XSS bug (unescaped `<` in `JSON.stringify`'d JSON-LD, `skills/platform/references/seo.md`) and fixed it as a prose edit — no regression gate was ever added for that bug class | The pack has no machine-checked security-rule category (`SEC-*`) at all; this is a directly evidenced gap, not a hypothetical one | Adopted as Phase 2 priority | Cited in `docs/CAPABILITY_MATRIX.md` Layer H; this is the strongest evidence in the whole audit for *why* security rules matter here specifically |
| 2026-08-25 | Screenshot rendering reproducibility (general infra knowledge, not a single fetched source) | Screenshot-based visual diffing is font/OS-sensitive; a baseline captured on a Windows dev machine will produce false diffs against Linux GitHub Actions runners purely from font rendering differences, independent of any real visual change | Baselines for the new visual-regression system must be captured and refreshed via a CI job on the same runner OS the diff check itself runs on, never captured locally and committed by hand | Adopted | Directly shaped the "`--update-baselines` supports local iteration, but the baseline that ships is the one CI produced" rule in the visual-regression design |

## Open questions for a future pass

- Whether `toHaveScreenshot()`'s built-in baseline management is worth adopting once the visual-regression system is promoted from informational to a blocking gate (see row above).
- Whether a lightweight Core Web Vitals proxy (e.g. a heuristic JS-payload + long-task budget, without real RUM infrastructure) is worth building given this repo has no deployed staging environment to collect real field data from.
- Whether APCA contrast checking (named as "the better perceptual check" in `core/accessibility-baseline.md` but explicitly deferred there — "WCAG 2 remains the shipping gate") has matured enough in browser/tooling support to revisit.
