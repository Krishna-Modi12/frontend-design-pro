# Research log

External findings that shaped a decision in this repo. Not a link dump — every row changed something (adopted, rejected with a reason, or is still open). Prioritizes official sources and primary documentation over blog posts, per this project's own bias toward verified-over-asserted.

| Date | Source | Finding | Implication | Status | Rationale |
|---|---|---|---|---|---|
| 2026-08-24 | Next.js official docs (`opengraph-image` file convention) | `opengraph-image.tsx` using `ImageResponse` is statically optimized (generated at build time, cached) unless it uses request-time APIs or uncached data | Compatible with `home/`'s `output: "export"` static-export mode, since the page has no dynamic route segments | Adopted | Verified by direct fetch of the official page rather than a search-result paraphrase — the one point of genuine technical uncertainty for the `home/` OG-image work |
| 2026-08-25 | Direct repo audit (this session) | No visual regression / screenshot-diffing tool exists anywhere in the repo (confirmed by search: no `pixelmatch`, no `toMatchSnapshot`, no Percy/Chromatic) despite `tools/screenshots/` already having Playwright + axe-core as dependencies and a capture-only script (`capture.mjs`) | The gap is real and the existing tooling is the right extension point — no need to introduce a parallel Playwright setup | Adopted | Grounded in direct file search, not assumption; shaped the "extend `tools/screenshots/`, don't invent a parallel structure" decision in the visual-regression plan |
| 2026-08-25 | Playwright's `toHaveScreenshot()` vs. `pixelmatch`+`pngjs` (evaluated, not fetched from external docs this pass — general framework knowledge) | `toHaveScreenshot()` requires the `@playwright/test` test runner and its own baseline/threshold/platform-pinning semantics, a bigger dependency and architecture shift than adding a lightweight pure-JS diff library to the existing `playwright-core`-based scripts | `pixelmatch` + `pngjs` chosen for the visual-regression system: no native deps, small footprint, fits the existing `tools/screenshots/` script style (plain `.mjs`, no test-runner wrapper) | Adopted | Open item: this comparison should be re-verified against current Playwright docs before the tool is promoted to a blocking gate, since `toHaveScreenshot()`'s baseline-management ergonomics may be worth the heavier dependency once the system is proven |
| 2026-08-25 | `docs/AUDIT.md` (this repo's own prior self-audit, dated 2026-08-10) | A manual LLM-driven audit found a real stored-XSS bug (unescaped `<` in `JSON.stringify`'d JSON-LD, `skills/platform/references/seo.md`) and fixed it as a prose edit — no regression gate was ever added for that bug class | The pack has no machine-checked security-rule category (`SEC-*`) at all; this is a directly evidenced gap, not a hypothetical one | Adopted as Phase 2 priority | Cited in `docs/CAPABILITY_MATRIX.md` Layer H; this is the strongest evidence in the whole audit for *why* security rules matter here specifically |
| 2026-08-25 | Screenshot rendering reproducibility (general infra knowledge, not a single fetched source) | Screenshot-based visual diffing is font/OS-sensitive; a baseline captured on a Windows dev machine will produce false diffs against Linux GitHub Actions runners purely from font rendering differences, independent of any real visual change | Baselines for the new visual-regression system must be captured and refreshed via a CI job on the same runner OS the diff check itself runs on, never captured locally and committed by hand | Adopted | Directly shaped the "`--update-baselines` supports local iteration, but the baseline that ships is the one CI produced" rule in the visual-regression design |

| 2026-08-25 | Direct implementation attempt (this session) | The visual-regression system's original scope (`demo/showcase` + `home/`) was wrong: `capture.mjs` already documents that showcase's hero is a WebGL particle field seeded at random ("every capture differs from the last"), which a first real run confirmed — a naive pixel diff against it would fail on every invocation regardless of any real change | Swapped `demo/showcase` for `demo/landing-page` (confirmed deterministic in the same `capture.mjs` comments) before shipping; a frozen-seed path for showcase is logged as follow-up in `docs/CAPABILITY_MATRIX.md`, not force-fit into this pass | Adopted | The plan's original scope was reasonable given what the audit had found, but implementation surfaced a fact the audit hadn't checked closely enough — worth recording so a future pass doesn't rediscover it by re-running the same failing experiment |

| 2026-08-25 | Direct analysis of `scripts/test_constraints.py`'s existing rule shapes, `docs/CHANGELOG.md`'s `SLOP-04` history (this session) | The four WCAG 2.2 SCs named in prose in `core/accessibility-baseline.md` (focus-not-obscured 2.4.11, target-size 2.5.8, dragging-alternative 2.5.7, redundant-entry 3.3.7) each resist a low-false-positive machine check: target-size needs an effective box size no regex/single-element AST check can compute; dragging-alternative has a clean negative signal but no reliable positive one; the other two are cross-element or cross-page properties a single-file check cannot see | Rejected as machine-checked rules this pass; kept as human-review items in `core/accessibility-baseline.md`, documented in `docs/CAPABILITY_MATRIX.md` rather than forced into a fragile rule | Rejected | `SLOP-04`'s own history — an anti-slop rule that shipped and passed its own designed-to-fail anti-example for several releases before anyone noticed — is the concrete proof that "the rule exists" and "the rule works" are different claims; better to say "human-review" honestly than repeat that failure under a WCAG label |

| 2026-08-25 | Direct measurement of `home/tokens.css` and `demo/landing-page/tokens.css` (this session) | Manually diffing every real OKLCH token pair in both files found no pair within ΔL≤1.5/ΔC≤0.015/ΔH≤3 that wasn't an exact-value alpha variant (`accent` vs `accent-glow`/`accent-wash`, same L/C/H, different alpha) — including one pair 4 points apart that `demo/landing-page/tokens.css`'s own comment says "read as one colour to anyone who is not measuring" but exists as two tokens for a measured contrast reason | The near-duplicate-color threshold in `tools/token-report/token-report.mjs` was set at that exact boundary and verified to fire on nothing in the real corpus while still catching a synthetic 0.3%-apart pair in the proof harness | Adopted | The alternative — a looser threshold — would have flagged the deliberate 4-point contrast pair as a false positive on its very first real run, undermining the "report, not gate" trust the tool depends on |
| 2026-08-25 | Grep survey of arbitrary Tailwind spacing brackets across `skills/`, `demo/`, `home/`, `core/` (this session) | Zero real occurrences of an off-4pt-scale arbitrary value on a padding/margin/gap utility exist anywhere in the corpus; the one arbitrary-bracket hit found (`demo/landing-page/components/HowItWorks.tsx`, `top-[0.55rem]`) is a `top` position offset, not a spacing-scale property | `core/design-tokens.md` scopes the 4pt-scale claim to "gap, pad and margin" specifically, not position offsets, which commonly need a precise non-scale value for optical alignment — `tools/token-report/token-report.mjs` excludes `top`/`left`/`right`/`inset` from the off-scale check for that reason | Adopted | Confirmed by grep before writing the check, not assumed — the narrower property scope was chosen because the wider one had a real, legitimate false-positive sitting in the corpus already |

| 2026-08-25 | Direct implementation attempt (this session) — Anti-slop 2.0's "context-aware, distinctive-and-appropriate" framing | The plan's Phase 3 target (score whether a design choice is distinctive-and-appropriate rather than merely banning specific patterns) is a holistic judgment about fit-to-brief, not a pattern-matching problem — the same shape that kept 4 WCAG 2.2 SCs and `SEC-01` (`dangerouslySetInnerHTML`) out of this pack's machine-checked rules earlier this pass | Rejected as a machine-checked rule this pass, honestly, rather than forced into a regex that would repeat `SLOP-04`'s own documented history of a rule that shipped and passed its own designed-to-fail anti-example for several releases | Rejected | Built the tractable, literal slice instead: `SLOP-06` bans `cursor-none`/`cursor: url(...)` (custom mouse cursors), one of the anti-slop wall's items with no "unless the brief asks" carve-out, matching the existing `SLOP-01..05` ban-list shape exactly rather than inventing a new architecture |
| 2026-08-25 | Direct measurement while adding `SLOP-06` to `scripts/test_constraints.py`'s `CONSTRAINTS` list (this session) | Bumping the regex-constraint count from 43 to 44 (60→61 total) produced figure drift across 32 files on the first `check_figures.py` run, plus 3 more found by hand (hard-wrap-straddling claims `check_anchored`'s second pass catches structurally but a simple per-line auto-fixer cannot relocate) — far larger than the security/visual-regression/token-report additions earlier this pass, which were deliberately kept outside the numbered 60 for exactly this reason | Proceeded with the sweep rather than reverting to a standalone tool, because — unlike those three — this is a natural extension of an *already-numbered, already-cascade-handled* system: `scripts/check_figures.py` computes every figure from the filesystem and told us exactly what to fix, and a small precise fixer (re-running each figure's own regex against its exact reported line, replacing only the drifted capture-group span) closed 32 of 35 mechanically in one pass | Adopted | Confirms the proportionality judgment applied all session (new category → ship outside the 60; extension of an existing category → the 60 is the right home, and the size of the doc sweep is a real but bounded, tooling-assisted cost, not a reason to avoid integration) |

| 2026-08-26 | Direct fetch of the `last30days-skill` (`github.com/mvanhorn/last30days-skill`) and `Agent-Reach` (`github.com/Panniantong/Agent-Reach`) repo READMEs (this session) | Both are self-contained host-side capability layers, not libraries a consumer imports: `last30days` runs a parallel engagement-scored search across Reddit/X/YouTube/HN/GitHub and reports readiness via `--preflight`; `agent-reach` is an MCP capability layer with `agent-reach doctor` health output and primary→backup backend fallback. Neither needs source vendored into a consuming repo, and each has a clean "not installed" state | `design-research` gains a `## Phase 0 — Social & trend signal` pass that prefers whichever tool is configured for engagement-ranked / platform-specific questions and falls back silently to `web_search` when neither is — detected-and-degraded exactly like Gate 7's missing TypeScript compiler | Adopted | Vendoring or hard-depending would violate `SECURITY.md`'s "this repo has no runtime" line and pull platform-auth concerns (Twitter/Reddit cookies) into a pack that ships only markdown; Gate 7's compiler posture already models the correct handling of an optional external capability, so the new phase reuses that rule rather than inventing one |

## Open questions for a future pass

- Whether `toHaveScreenshot()`'s built-in baseline management is worth adopting once the visual-regression system is promoted from informational to a blocking gate (see row above).
- Whether a lightweight Core Web Vitals proxy (e.g. a heuristic JS-payload + long-task budget, without real RUM infrastructure) is worth building given this repo has no deployed staging environment to collect real field data from.
- Whether APCA contrast checking (named as "the better perceptual check" in `core/accessibility-baseline.md` but explicitly deferred there — "WCAG 2 remains the shipping gate") has matured enough in browser/tooling support to revisit.
