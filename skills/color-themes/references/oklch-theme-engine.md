# OKLCH Theme Engine

Generating a complete token set from one anchor colour, in a space where the
arithmetic means what it looks like.

## Why OKLCH and not HSL

HSL's `L` is not lightness. It is the midpoint of the largest and smallest RGB
channel, which has almost nothing to do with perception:

```
hsl(60 100% 50%)   →  yellow, relative luminance ≈ 0.93
hsl(240 100% 50%)  →  blue,   relative luminance ≈ 0.07
```

Same declared lightness, roughly a 13× difference in the thing eyes actually
measure. Every ramp generated by stepping HSL lightness is therefore uneven, and
every hue rotation at "constant lightness" changes brightness. The author cannot
see the bug because the numbers agree with each other.

OKLCH is perceptually uniform. `oklch(60% 0.15 60)` and `oklch(60% 0.15 240)`
genuinely look equally bright. That single property is what makes a generated
palette possible at all.

| Channel | Range | Meaning |
|---|---|---|
| `L` | 0–100% | Perceived lightness. 0 black, 100 white. |
| `C` | 0–~0.37 | Chroma — distance from grey. Unbounded in theory, gamut-bound in fact. |
| `H` | 0–360 | Hue angle. 0 pink-red, 145 green, 260 blue. |

CSS takes it directly: `oklch(72.4% 0.181 156.3)`. Support is universal in
current browsers; `@supports (color: oklch(0% 0 0))` if you must gate.

## Lightness scale

Fix the steps, then move hue and chroma under them. Consistent lightness across
themes is what makes two brand colours feel like the same system.

| Token | Light theme L | Dark theme L |
|---|---|---|
| `surface` | 98.5% | 17.4% |
| `elevated` | 100% | 20.1% |
| `border` | 91.0% | 26.8% |
| `muted` | 55.0% | 63.2% |
| `text` | 18.8% | 96.2% |

Never 0% or 100% for a large area. Pure black surfaces produce halation against
bright text on OLED, and pure white is the harshest surface a screen can emit —
both are why real design systems land near 98.5% and 17.4% rather than the ends.

## Chroma must fall off at the extremes

The sRGB gamut is widest in the middle and pinches to a point at both ends. Hold
chroma constant across a lightness ramp and the light end clips to neon while the
dark end clips to mud.

```ts
/** Chroma the gamut can actually hold at a given lightness. */
function maxChroma(l: number): number {
  const t = l / 100;
  // Triangular falloff: peaks near L=0.5, zero at both ends.
  return 0.37 * (1 - Math.abs(t - 0.5) * 2) ** 0.65;
}

const chroma = Math.min(requested, maxChroma(lightness));
```

This is an approximation — the true gamut boundary depends on hue, and yellow
reaches far higher chroma than blue at the same lightness. For a theme engine the
approximation is the right trade: it never clips, and the error is on the
conservative side. If you need the exact boundary, binary-search lightness/chroma
until the round-trip through sRGB stops changing the value.

## Harmonic schemes

Rotation on the hue wheel. In OKLCH the rotated colours keep their weight, which
is the thing HSL gets wrong.

| Scheme | Offsets | Reads as |
|---|---|---|
| Complementary | +180° | maximum tension, one accent against one field |
| Split-complementary | ±150° | complementary contrast, less strident |
| Triadic | ±120° | three equal voices — needs one to dominate |
| Analogous | ±30° | calm, low contrast, single-mood |
| Tetradic | +90, +180, +270 | four colours, two pairs — hardest to balance |

```ts
export type Scheme = "complementary" | "split" | "triadic" | "analogous";

const OFFSETS: Record<Scheme, number[]> = {
  complementary: [0, 180],
  split: [0, 150, 210],
  triadic: [0, 120, 240],
  analogous: [0, 30, -30],
};

function scheme(baseHue: number, kind: Scheme): number[] {
  return OFFSETS[kind].map((d) => (baseHue + d + 360) % 360);
}
```

The modulo matters: a negative hue is invalid in CSS and, depending on the
browser, either clamps to 0 or invalidates the whole declaration.

Rotation alone is not a palette. A triadic set of three equally saturated colours
is a flag, not an interface. Pick one to carry the accent, drop the others to a
fraction of the chroma, and use them for state rather than for surfaces.

## Generating the token set

```ts
export interface ThemeTokens {
  surface: string;
  elevated: string;
  border: string;
  muted: string;
  text: string;
  accent: string;
}

export function generateTheme(hue: number, dark: boolean): ThemeTokens {
  const c = (l: number, mult: number) => {
    const chroma = Math.min(0.02 * mult, maxChroma(l));
    return `oklch(${l}% ${chroma.toFixed(3)} ${hue})`;
  };

  return dark
    ? {
        surface: c(17.4, 0.6),
        elevated: c(20.1, 0.7),
        border: c(26.8, 0.7),
        muted: c(63.2, 0.9),
        text: c(96.2, 0.25),
        // Chroma reduced on dark: saturated colour on a near-black field glows.
        accent: `oklch(72.4% ${Math.min(0.14, maxChroma(72.4))} ${hue})`,
      }
    : {
        surface: c(98.5, 0.05),
        elevated: c(100, 0),
        border: c(91.0, 0.4),
        muted: c(55.0, 0.9),
        text: c(18.8, 0.65),
        accent: `oklch(58.0% ${Math.min(0.19, maxChroma(58))} ${hue})`,
      };
}
```

Two things this encodes that are easy to miss:

**Surfaces carry a trace of the accent hue.** A theme whose greys are truly
neutral (`C = 0`) looks disconnected from its accent. A chroma of 0.01–0.02 at
the same hue is invisible as colour and unmistakable as cohesion.

**Dark accents are less saturated than light ones**, not more. The instinct is to
push chroma up to compensate for the dark field; the result vibrates. Roughly
0.75× the light-theme chroma is the right direction.

## Converting to and from sRGB

You need this to read colours out of an image, and to sanity-check that a
generated colour is inside the gamut. It is about forty lines and no dependency.

```ts
const f = (x: number) => (x <= 0.04045 ? x / 12.92 : ((x + 0.055) / 1.055) ** 2.4);
const g = (x: number) => (x <= 0.0031308 ? 12.92 * x : 1.055 * x ** (1 / 2.4) - 0.055);

export function rgbToOklch(r: number, gg: number, b: number) {
  const lr = f(r / 255), lg = f(gg / 255), lb = f(b / 255);

  const l = Math.cbrt(0.4122214708 * lr + 0.5363325363 * lg + 0.0514459929 * lb);
  const m = Math.cbrt(0.2119034982 * lr + 0.6806995451 * lg + 0.1073969566 * lb);
  const s = Math.cbrt(0.0883024619 * lr + 0.2817188376 * lg + 0.6299787005 * lb);

  const L = 0.2104542553 * l + 0.7936177850 * m - 0.0040720468 * s;
  const A = 1.9779984951 * l - 2.4285922050 * m + 0.4505937099 * s;
  const B = 0.0259040371 * l + 0.7827717662 * m - 0.8086757660 * s;

  return {
    l: L * 100,
    c: Math.sqrt(A * A + B * B),
    h: ((Math.atan2(B, A) * 180) / Math.PI + 360) % 360,
  };
}
```

The cube roots are the perceptual part — they are what turns linear light into
something that steps evenly. Skipping them (as a naive "LMS" conversion does)
gives you a space no better than the one you left.

The inverse, for gamut checks:

```ts
export function oklchToRgb(L: number, C: number, H: number) {
  const a = C * Math.cos((H * Math.PI) / 180);
  const b = C * Math.sin((H * Math.PI) / 180);
  const ll = L / 100;

  const l = (ll + 0.3963377774 * a + 0.2158037573 * b) ** 3;
  const m = (ll - 0.1055613458 * a - 0.0638541728 * b) ** 3;
  const s = (ll - 0.0894841775 * a - 1.2914855480 * b) ** 3;

  return {
    r: g(4.0767416621 * l - 3.3077115913 * m + 0.2309699292 * s) * 255,
    g: g(-1.2684380046 * l + 2.6097574011 * m - 0.3413193965 * s) * 255,
    b: g(-0.0041960863 * l - 0.7034186147 * m + 1.7076147010 * s) * 255,
  };
}
```

A channel outside 0–255 means the colour is outside sRGB. That is the gamut check:
convert, and if anything is out of range, reduce chroma and try again.
